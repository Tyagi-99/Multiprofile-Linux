# Build Trust Before Claiming Browser Parity

Multiprofile Linux can become a dependable Linux profile manager sooner than it can become an AdsPower, GoLogin, or Multilogin equivalent. **Fix the measured contradictions in its browser identity, prove proxy isolation under failure, and ship a maintained browser and update path before moving valuable accounts to it.** A proxy changes the exit IP; it does not correct the Windows claim that the live test saw disagree with a service worker and a CSS screen query. The current build uses stock host Chromium plus DevTools overrides and injected scripts, while the commercial vendors document maintained browser cores and coordinated profile controls. Their documentation establishes advertised features, **not independently verified resistance to detection**. The practical choice is to release a narrower, honest Linux profile product first, or fund a continuing browser-engine program before making a cross-OS anti-detection claim. ## Close the two contradictions observed on a real checker

On one fresh, direct profile, **the page claimed Windows and 1366 × 768, while original CreepJS reported Linux user-agent data in a service worker and 2560 × 1600 through a CSS screen query**. Stock Chromium on the same host reported its native Linux and screen values in those checks. A separate simple worker probe reportedly returned Windows, so the service-worker result needs a targeted reproduction rather than an assumption that every worker fails. The project's internal audit reports page and worker agreement across its own probes; the live path shows that the probe set is incomplete. The separate creepjs.org checker gave Multiprofile 97/100 and flagged sparse fonts, while Pixelscan labeled both Multiprofile and clean Chromium inconsistent and masking detected. **Neither checker headline is a release gate by itself.** These captures cover one host and one profile, and do not establish acceptance rates on account sites. ([Multiprofile capture](/home/davish/.codex/visualizations/2026/10/05/01a10bf5-aaba-79c3-a361-6162165ade3e/creepjs_original.json); [stock control](/home/davish/.codex/visualizations/2026/10/05/01a10bf5-aaba-79c3-a361-6162165ade3e/stock_chromium_creepjs_original.json); [internal audit](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/docs/04_FINGERPRINT_TEST_RESULTS.md); [checker result](/home/davish/.codex/visualizations/2026/10/05/01a10bf5-aaba-79c3-a361-6162165ade3e/creepjs_checker.json); [Pixelscan result](/home/davish/.codex/visualizations/2026/10/05/01a10bf5-aaba-79c3-a361-6162165ade3e/pixelscan_checker.json))

First, reproduce both failures in an automated test that visits the actual service-worker and CSS media-query paths. Capture a versioned identity manifest from HTTP headers, page JavaScript, iframes, dedicated/shared/service workers, CSS, fonts, GPU, screen and window geometry, locale, and timezone. Compare each supported preset with a real reference device running the same engine version and with stock Chromium on the host. **Pass only when the same profile makes compatible claims across these surfaces on first load, new tabs, and restart.** Fix the root cause and the sparse font environment; aliases alone cannot change a font file's internal metadata. If a Windows identity cannot meet this gate, offer a coherent native-Linux mode and label cross-OS emulation experimental. This is a quality target, not a claim that Linux profiles cannot be linked. ([font audit](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/docs/04_FINGERPRINT_TEST_RESULTS.md); [fontconfig implementation](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/src/multiprofile/browser/fontconfig.py); [Multilogin inconsistency guidance](https://multilogin.com/help/en_US/common-issues/browser-fingerprint-inconsistencies); [GoLogin fingerprint guidance](https://support.gologin.com/en/articles/14810056-profile-fingerprint-settings))

## Prove the proxy route throughout a session

The current launcher passes a configured upstream proxy directly to Chromium; direct profiles use the host connection. Its prelaunch proxy check defaults to blocking a failed proxy, but explicit `WARN` and `ALLOW` settings permit a host-IP launch. A prelaunch check cannot prove that a later disconnect, WebRTC path, DNS lookup, IPv6 connection, WebSocket, worker, or download stays on the intended route. **A proxy subscription alone therefore cannot repair the observed page/worker/CSS discrepancies or establish leak safety.** AdsPower, GoLogin, and Multilogin document proxy assignment and checks together with fingerprint or location settings, but those are vendor descriptions rather than independent tests of this project's behavior. ([network code](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/src/multiprofile/network.py); [AdsPower settings](https://help.adspower.com/docs/global_settings); [GoLogin proxy management](https://support.gologin.com/en/articles/14810002-adding-and-managing-proxies); [Multilogin proxy FAQ](https://multilogin.com/help/en_US/multilogin-proxy-faq))

Make `BLOCK` the supported mode for accounts that require a fixed route, and make direct fallback an explicit, visible exception. Test direct, HTTP(S), SOCKS5, authenticated, and dead proxies using both a destination-side echo server and host packet capture. Assert exit IP, DNS, IPv6, WebRTC, and location consistency at launch and after deliberately cutting the proxy mid-session; repeat after restart and across tabs, workers, WebSockets, and downloads. Store the route identity and check results with the profile, and flag an unexpected IP or country change before continuing a session. This gate should be judged by measured traffic, not only the app's health-check response. ([network isolation specification](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/docs/NETWORK_ISOLATION.md); [network code](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/src/multiprofile/network.py))

## Choose the browser scope before funding transport work

The repository records **no TLS/JA3/JA4 or HTTP/2 identity alignment**, and its Windows claim currently rides on stock host Chromium, DevTools overrides, and injected scripts. A normal HTTP CONNECT or SOCKS tunnel carries the browser's destination TLS and HTTP/2 behavior through it; changing those signatures requires a new transport implementation or a maintained browser-core change. The roadmap's statement that all traffic already passes through a local product-controlled proxy conflicts with the launcher, which points Chromium at an upstream proxy only when one is configured. The roadmap's proposed “local proxy rewrite” is therefore a new subsystem with HTTPS, HTTP/3, WebSocket, authentication, certificate, and compatibility work, not a small extension of current routing. BrowserLeaks recorded a TLS fingerprint but no matched Windows reference trace was captured, so **a specific transport mismatch is not yet proven by a controlled comparison**. ([feature matrix](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/docs/03_FEATURE_MATRIX.md); [CDP injection](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/src/multiprofile/browser/cdp_inject.py); [roadmap](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/docs/06_ROADMAP.md); [network code](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/src/multiprofile/network.py); [BrowserLeaks capture](/home/davish/.codex/visualizations/2026/10/05/01a10bf5-aaba-79c3-a361-6162165ade3e/browserleaks_tls.json))

There are two defensible targets. **The near-term product** is a reliable Linux profile and proxy manager with a native Linux identity, persistent storage, automation API, and honest limits. **The parity program** is a pinned, maintained Chromium-based build with identity controls below page-script injection, plus font and network behavior tested against real reference browsers. AdsPower documents Chrome- and Firefox-based cores; GoLogin documents Orbita; Multilogin documents Mimic and says its Firefox-based Stealthfox no longer receives new core updates. Those claims show how much ongoing core maintenance the category entails. A second Firefox core, cloud sync, team accounts, and proxy marketplace should follow an explicit customer and budget decision; none fixes today's contradictions. ([AdsPower profile guide](https://help.adspower.com/docs/creating_browser_profiles); [GoLogin Orbita guide](https://support.gologin.com/en/articles/14853789-orbita-browser); [Multilogin browser cores](https://multilogin.com/help/en_US/how-to-use-mimic-and-stealthfox); [project feature matrix](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/docs/03_FEATURE_MATRIX.md))

## Ship in phases with observable release gates

The following effort ranges are **planning estimates**, assuming one experienced full-time browser/network engineer with part-time QA and release help; they are not measured delivery times. Work can overlap, but a maintained core also creates a permanent security-update obligation.

| Phase | Estimated effort | Deliverable and exit gate |
|---|---:|---|
| 0. Establish the baseline | 2–4 weeks | Reproducible live-checker captures and a reference/control matrix by engine version, Linux distro, display system, preset, and proxy type. Record raw mismatches instead of one score. |
| 1. Correct identity and route failures | 1–3 months | No contradictory OS, version, screen, language, worker, or GPU claims in supported presets; packet-level proof of proxy egress and no host-IP fallback in supported `BLOCK` mode after a mid-session proxy drop. Keep unsupported presets out of release claims. |
| 2. Release a dependable Linux product | 1–3 months after the baseline | Publish a signed package and live update channel; document supported browser versions and security response; pass backup/restore, crash recovery, profile migration, and 24-hour session tests. Provide simple Python/Node start/stop/CDP examples and redacted diagnostics. |
| 3. Attempt commercial identity parity | 6–12+ months for a focused team, then continuing maintenance | Maintain a browser core or validated equivalent; compare server-observed TLS, ALPN, HTTP/2 and HTTP/3 with genuine same-version references through each route; rerun all identity, isolation, compatibility, and update gates every release. Claim only the presets and environments actually passing. |

The project already has profile storage, backups, scoped API tokens, bulk operations, CI-tested signed-update tooling, and a deliberate 150-stored/20-running target. Its documentation says the production signing key and package repository have not been published, and the installed browser is supplied by the host. **A buildable update system is not yet an operating update channel.** Chrome's release cadence makes browser patch ownership a recurring task, whether the project follows system Chromium or maintains its own core. ([API documentation](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/docs/API.md); [feature matrix](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/docs/03_FEATURE_MATRIX.md); [update documentation](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/docs/UPDATES.md); [installation](https://github.com/Tyagi-99/Multiprofile-Linux/blob/main/docs/INSTALLATION.md); [Chrome release channels](https://www.chromium.org/chrome-release-channels/))

Before release, reconcile three material document conflicts: the network specification says `--host-resolver-rules` enforces proxy DNS although the code removed that flag; its “fail-closed” language needs the `WARN`/`ALLOW` exceptions stated beside it; and the roadmap's existing local-proxy premise is false for current routing. Update the audit's stale claim that no public checker has been visited and publish the October 5 observations with their one-host limitation. Documentation should state measured behavior and supported modes precisely, because users will otherwise mistake a design intention for a deployed safety property. ## Conclusion

The project's next meaningful milestone is **a profile whose identity and network route stay coherent under real public-site and failure tests**, followed by an update channel that keeps that behavior stable. Once those gates pass, the team can decide whether customers need a strong Linux workflow product or whether sustained engine work is justified. No independent, matched benchmark of AdsPower, GoLogin, and Multilogin was available here, so “their level” must remain a measurable engineering target rather than a promised detection outcome.
